## R5: ISTRING / IVECTOR / IUVECTOR evaluation policy

### Finding restated

The interpreted dispatcher (`mdl/runtime/core.rkt:1105-1107` at 850a87f)
and the compiled dispatcher (`core.rkt:1567-1569`) special-cased
`(eq? fn mdl-istring)` / `mdl-iuvector` / `mdl-ivector` and called
`mdl-*-raw` with the unevaluated argument data. The SUBR values reached
through APPLY and MAPF (`mdl-ivector` `core.rkt:2452`, `mdl-iuvector`
`core.rkt:2492`, `mdl-istring` `core.rkt:3019`) just copied the supplied
value. The two kinds of path disagreed.

### Manual contract and reference observations

Manual §7.5.4 (fetched from mdl-language.readthedocs.io, chapter 7):
"Each of the SUBRs ILIST, IVECTOR, IUVECTOR, and ISTRING" ... when the
expression is supplied "it is re-EVALuated each time a new element is
generated" and "EVAL of expression is re-EVALuated, since all of these are
SUBRs." Example: `<SET A 0> <IUVECTOR 9 '<SET A <+ .A 1>>>` gives
`![1 2 3 4 5 6 7 8 9!]`. ISTRING errors on a non-CHARACTER result.

So the argument is evaluated once, like any SUBR argument, and its *value*
is EVALed once per element. Evaluating twice in total for a quoted FORM is
the documented contract, not an accidental double evaluation.

Pinned Confusion probes:
`docs/evidence/M3/review/r5-constructor-eval-cases.json` produced
`docs/evidence/M3/review/r5-constructor-eval-reference.json` (20 cases,
one process per case, stdin then `<QUIT>`, no RNG involvement). Results:

| case | Confusion |
| --- | --- |
| `<IVECTOR 3 '<SET A <+ .A 1>>>` direct / via APPLY | `[1 2 3]`, A=3 (both) |
| `<IVECTOR 3 <SET A <+ .A 1>>>` | `[1 1 1]`, A=1 |
| `<IVECTOR 3 5>`, `<APPLY ,IVECTOR 2 7>` | `[5 5 5]`, `[7 7]` |
| `<IVECTOR 3 .X>` with X a FORM | `[1 2 3]` |
| `<MAPF ,LIST ,IVECTOR '(2 3) '(<SET A ..+1> <SET A ..+10>)>` | `([1 2] [12 22 32])` |
| `<IVECTOR !.L>` with L `(2 7)` / `(3 '<SET ...>)` | `[7 7]` / `[1 2 3]` |
| `<IVECTOR 2 [1 2]>` | elements `=?` but not `==?` (fresh VECTOR per element) |
| `<ISTRING 3 '<ASCII <SET A ..>>>` direct / APPLY | `"ABC"` (both) |

**Recorded deviation.** Confusion's IUVECTOR runs the expression one extra
time (`![2 3 4!]`, A=4). This contradicts the manual's own example
(`![1 2 ... 9!]`). The runtime follows the manual (`![1 2 3!]`, A=3); the
test file says so. No original-source call depends on this: every IUVECTOR
use passes a constant.

### Root cause

There were two evaluation policies. The `-raw` path
(`core.rkt:2460`, `2500`, `3027`) parsed raw argument data itself. It
evaluated the size and fill with `mdl-eval` and EVALed the fill value per
element (`core.rkt:2470`, `2510`, `3035`). This matched the manual for a
plain direct call, but it skipped argument assembly, so SEGMENT (`!`)
arguments raised ILLEGAL-SEGMENT. In compiled code it also skipped the
compiled argument thunks. The ordinary SUBR procedure never EVALed the fill
value. So APPLY and MAPF put the FORM itself in every element, and ISTRING
rejected the FORM.

### Design decision

I made the constructors ordinary SUBRs and removed both dispatcher special
cases. The arguments arrive already evaluated, through the normal SUBR
argument path on every call route. `constructor-fill-thunk` EVALs the fill
value once per element, in element order. No callable-kind abstraction is
needed, because the reference behaviour is plain SUBR behaviour. An
already-evaluated argument is EVALed once more, per element. That is the
documented contract. It is a no-op for self-evaluating values: FIX,
CHARACTER, FALSE, ATOM, STRING. LIST, VECTOR and UVECTOR values are rebuilt
per element, as Confusion shows.

Original-source uses (all in `patched_confusion/*.mud`):
`<IVECTOR 256 0>`, `<IUVECTOR <LENGTH ,VILLAINS> 0>`,
`<IVECTOR <LENGTH ,VILLAINS> '<>>`, `<ISTRING 8 !\ >`,
`<IVECTOR <LENGTH .PAIRS>>`, `<IVECTOR 5 <>>`, `<IVECTOR 3>`,
`<ISTRING 5>`, `<IVECTOR 10 <>>`, `<ISTRING 32>`, `<ISTRING .TLEN !\ >`,
`<ISTRING 8>`, `<IUVECTOR 20>`, `<ISTRING 100>`, `<IVECTOR 3 #FALSE ()>`,
`<IVECTOR 10 '<REST <ISTRING 5> 5>>`. All give the same values under the
single policy. `'<>` evaluates to the empty FORM, and EVAL of that per
element gives `#FALSE ()`. This has a regression test. The quoted REST fill
gives ten distinct empty views; regression tested on the direct and APPLY
paths. The full source still loads (see commands).

## R7: shared STRING views as primitive arguments

### Finding restated

A STRING can be a native Racket string or a `mdl-string-view` (shared
storage from REST). Several consumers checked `(string? x)` and so
rejected views.

| --- | --- | --- | --- |

| ATOM SUBR | `core.rkt:3294` | rejected view; **aliased PNAME** | accepts; PNAME = immutable copy |
| EVENT (name, priority) | `core.rkt:1946` | rejected view; stored user's mutable STRING as event key | accepts; key = immutable copy |

A second defect turned up during the audit. INSERT and ATOM used the
caller's mutable STRING itself as the PNAME, and also as the `equal?`-hashed
OBLIST key. A later `<PUT ,S 1 !\Z>` renamed the atom and corrupted the
OBLIST bucket.

### Reference observations

Probes: `docs/evidence/M3/review/r7-string-view-cases.json` produced
`docs/evidence/M3/review/r7-string-view-reference.json` (17 cases). Confusion
accepts REST views in LOOKUP, INSERT, ATOM, REMOVE, EVENT (the view and the
equal native name give the same IHEADER), STRING, PRINTSTRING and `=?`.
`==?` is true for two equal RESTs of the same STRING, and false against an
equal literal. After INSERT or ATOM, a PUT on the parent or on the view is
visible through both (`"XZSEVQRT"` / `"ZSEVQRT"`). The atom's SPNAME stays
`"RSEVQRT"`, and `LOOKUP "RSEVQRT"` still finds it. That shows PNAME copy
semantics. LOOKUP with a FIX, INSERT with a CHARACTER, ATOM with a FIX, and
SPNAME with a STRING all error.

### Design decision

I added one helper, `mdl-string-snapshot who value message` (exported from
core). It accepts any MDL STRING, native or view, rejects every other TYPE
with an explicit error, and returns an immutable copy of the visible
characters. It is used only where the manual's semantics is a copy: atom
PNAMEs, OBLIST keys, EVENT names, and host file paths. The user's STRING is
never detached. Views keep sharing storage with the parent, and the tests
check mutation visibility through both parent and view after INSERT or ATOM.
Typed STRING values (a CHTYPEd NEWTYPE) are still rejected, as before.

## Remaining risks and unsupported cases

- The runtime has no `EVAL` SUBR, so the interpreted path is tested through
  `mdl-eval` and FUNCTION bodies, not `<EVAL '...>`.
- ILIST is not implemented in the runtime. When it is added, it must use
  `constructor-fill-thunk`.
- The IUVECTOR fill count on success differs from Confusion (manual
  followed, recorded above). On a uniform-type failure, the counts agree
  (see the review follow-up).
- Channel mode checks (`(equal? (mdl-nth channel 2) "PRINT")`) compare
  native strings only. All channels are runtime-constructed today; a
  user-built CHANNEL whose mode is a REST view would be rejected, which
  fails safe.
- SPNAME returns an immutable copy, not storage shared with the PNAME. This
  was not changed here.

### M3 review: constructor evaluation policy (R5)

Manual §7.5.4 defines ILIST, IVECTOR, IUVECTOR and ISTRING as SUBRs. ILIST
is not yet implemented. Every call path (compiled call, interpreted FORM or
FUNCTION body, APPLY, MAPF) evaluates the arguments once, including `!`
SEGMENT splicing, before the procedure runs. The optional second argument's
value is then EVALed once per generated element, in element order.
`<IVECTOR 3 '<SET A <+ .A 1>>>` yields `[1 2 3]`.
`<IVECTOR 3 <SET A <+ .A 1>>>` evaluates its argument once and yields
`[1 1 1]`. A VECTOR fill is rebuilt per element (`=?` but not `==?`).
ISTRING requires each per-element result to be a CHARACTER. IUVECTOR
validates each value as it is produced: the first value fixes the UTYPE,
STRING is never permitted, and a mismatched value fails immediately, so
later fills are not evaluated. No dispatcher special-cases these
constructors.

Pinned Confusion agrees for IVECTOR and ISTRING on all paths, and for the
IUVECTOR failure counts. **Recorded deviation:** on success, Confusion's
IUVECTOR evaluates the fill once extra, a discarded evaluation used to fix
the type (`<IUVECTOR 3 '<SET A <+ .A 1>>>` gives `![2 3 4!]`, A=4). This
contradicts the manual's own example (`![1 2 ... 9!]`). The runtime follows
the manual (`![1 2 3!]`, A=3). No original-source call is affected. Evidence:
`evidence/M3/review/r5-constructor-eval-reference.json`,
`evidence/M3/review/r5-iuvector-uniform-reference.json`.

### M3 review: STRING views as primitive arguments and PNAME snapshots (R7)

Any primitive that takes a STRING accepts a native STRING or a shared REST
view. Other TYPEs, including CHTYPEd STRING-primtype values, fail
explicitly.

**PNAME snapshot rule:** a primitive that retains a name takes an immutable
copy of the STRING's visible characters at the moment of the call
(`mdl-string-snapshot`). This covers INSERT and ATOM (the PNAME), LOOKUP and
REMOVE (the OBLIST key), EVENT (the event name) and FLOAD (the host path).
A PNAME therefore never aliases user storage. A later PUT on the original
STRING, or on any view of it, changes neither the atom's name nor OBLIST
lookup. The parent STRING and its views keep sharing storage with each
other. STRING, PRINTSTRING, `=?` and `==?` read a view's visible range
directly. Evidence: `evidence/M3/review/r7-string-view-reference.json`.
