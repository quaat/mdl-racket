## The finding

At 850a87f, `mdl-error` (`mdl/runtime/core.rkt:3069-3091`) handled an error in
three steps:

1. It created a live ERROR FRAME.
2. It called `mdl-emit-event! "ERROR"` (`:3087`), which appends the occurrence
   to the session pending queue and then drains the queue.
3. It raised a host error.

`mdl-erret` (`:3093-3098`) jumped to the frame's escape continuation. Handler
delivery (`mdl-deliver-occurrence!`, `:1874-1889`) restores the previous
interrupt level in a `dynamic-wind` post thunk. It then drains pending
occurrences, but only on a normal return.

## Reproductions (red)

### B1. ERROR occurrence queued behind older pending occurrences

The ERROR occurrence went through the ordinary queue. An older eligible
occurrence was drained first. If that older handler raised, the ERROR
occurrence stayed in the queue after its ERROR call had failed and its FRAME was
dead. The next safe point then delivered a stale ERROR occurrence. The handler
for the real error never ran.

Scratch reproduction at 850a87f. Script:
`/tmp/claude-1000/-home-thomas-project-racket-mdl-racket-zork-harness/a2d814ab-1670-4777-b6de-16c1519c5338/scratchpad/r8/stale.rkt`.

```
<ERROR PROBE> => raised: e-handler: E-BOOM 2          ; the ERROR handler did not run
error handler calls so far: 0
ERROR handler call 1 args ("PROBE")                    ; stale delivery at a later safe point
<INT-LEVEL 0> (later safe point) => raised: mdl-erret: ERRET requires a live ERROR FRAME in this session
```

### B2. ERRET and the interrupt level

ERRET escaped through the delivery `dynamic-wind`. That always restored the
level from before the interrupt. Two consequences:

1. It overrode a handler's explicit `<INT-LEVEL 0>` whenever the interrupted
   level was not zero.
2. It skipped the post-delivery drain. An occurrence queued during the handler
   could stay pending while the level was already low enough to deliver it.

## Root cause

- **B1:** `core.rkt:3087` (850a87f) routed an undeferrable ERROR occurrence
  through `mdl-emit-event!`. That function enqueues first and delivers in queue
  order (`:1814-1818`, `:1891-1907`).
- **B2:** the delivery `dynamic-wind` post thunk (`:1887`) restores the old level
  on every exit, including the ERRET continuation jump. The trailing
  `mdl-drain-pending!` (`:1889`) only runs on a normal return.

## Manual contract and Confusion observations

Manual chapter 21 (mdl-language.readthedocs.io, "21-interrupts"), as fetched:

- **§21.8.11:**
  - Handlers receive the FRAME of the ERROR call and the TUPLE of arguments.
  - "real ERROR will be called, because "ERROR" interrupts cannot be queued".
  - A handler that resolves the error "can ERRET with a value from the ERROR
    FRAME, after having done `<INT-LEVEL 0>`".
  - "If no handler takes care of the error, it falls into the normal ERROR".
- **§21.7.1:** after the actions of an interrupt complete, "the previously-existing
  interrupt level is restored", and queued occurrences are processed in their
  original order.
- **§21.7.3:** `DISMISS` returns to an arbitrary activation "at an arbitrary
  interrupt level". If the level is omitted, the level from before the interrupt
  is restored.
- The chapter does not say what other non-local exits do to `INT-LEVEL`.

Interpretation: §21.8.11 tells the handler to lower the level itself before
ERRET, and the original `HANDLE` (`77rooms.mud:224-246`) does `<INT-LEVEL 0>`
before each `<ERRET T .FRM>`. So ERRET does not restore the level from before
the interrupt. The level on resumption is the one current when ERRET ran. Only
normal handler completion, or `DISMISS`, restores it. `DISMISS` is not
implemented.

## Design decision

1. **ERROR is delivered directly, never queued.** When the ERROR IHEADER is
   enabled and its priority is above the current level, `mdl-error` calls
   `mdl-deliver-occurrence!` for its own occurrence. It no longer calls
   `mdl-emit-event!`. Older pending occurrences are still drained by that
   delivery after the handler returns normally, or at the next safe point. At or
   above the ERROR priority, the real error is raised as before.
2. **ERRET resumes at the level current when it ran.** `mdl-erret` passes the
   current level along with the value. `mdl-error` reinstates that level after
   the `call/ec` returns, which undoes the restorations made by handler cleanup
   during unwinding. As a result:
   - occurrences queued while the handler ran stay queued until the level is
     lowered;
   - returning from ERROR is a safe point: right after the level is
     reinstated, `mdl-error` calls `mdl-drain-pending!`. Occurrences with a
     priority above the resumed level (e.g. left pending by an earlier raising
     handler) are delivered exactly once; lower ones stay queued. No occurrence
     is left eligible but undelivered (review follow-up, see below);
   - the source pattern `<INT-LEVEL 0> <ERRET T .FRM>` yields level 0 for any
     interrupted level.
3. **Normal return and host exceptions are unchanged.** On a normal handler
   return (fallthrough), and when a host exception leaves a handler, the
   previous level is still restored. That is the existing #104 contract. FRAME
   liveness is still cleared by the `dynamic-wind` in `mdl-error`.

### Hypothesis (a): primitive failures

Hypothesis (a) is reproduced: `<+ 1 "a">`, an unbound LVAL and `</ 1 0>` raise
host exceptions, and a registered ERROR handler is not called. This is pinned by
the last test scenario.

Decision: keep these as strict host failures. Routing them through the ERROR
interrupt would need several things that do not exist yet:

- a faithful catalogue of MDL error ATOMs and argument shapes (e.g.
  `ARG-WRONG-TYPE!-ERRORS`, `UNBOUND-VARIABLE!-ERRORS`, `CONTROL-G?!-ERRORS`,
  `FILE-SYSTEM-ERROR!-ERRORS`);
- a FRAME for every SUBR call site;
- resumable SUBR returns.

Confusion does not route its SUBR errors through ERROR either. No blanket
conversion of host exceptions was added.

Source impact:

- `77rooms.mud:259-271` installs `HANDLE` on `<EVENT "ERROR" 8>`. One handler
  stays active; the second registration is turned OFF.
- `HANDLE` resolves only `CONTROL-G?!-ERRORS` (a terminal ^G) and
  `FILE-SYSTEM-ERROR!-ERRORS` "ILLEGAL CHR AFTER CNTRL P ON TTY DISPLAY" (an ITS
  TTY error).
- For the debugging users in `WINNERS` it returns normally and falls into the
  real error.
- For anything else it prints an apology and calls `FINISH`.

Both resolvable errors come from host or terminal sources that do not exist
here. Every other path is a crash report that needs `FINISH` and CHANNEL
support, which is unsupported. Explicit `<ERROR ...>` calls in the source still
reach `HANDLE`:

- `81prim.mud:5,18,31,54,62,72,86`;
- `77makstr.mud:45,129`;
- `77defs.mud:458`;
- `78melee.mud:462`;
- `81tell-repl.mud:133`.

So the limitation affects only:

- the ^G and TTY recovery paths;
- crash reporting after a primitive failure. With this runtime that is a strict
  host failure instead of the apology and `FINISH`.

## Remaining risks and unsupported cases

- **ERRET level semantics:** the behaviour that ERRET keeps the current level
  rests on the manual's §21.8.11 wording and on the original handler's pattern.
  The manual does not state it as a rule, and Confusion cannot observe it
  because its EVENT and HANDLER are stubs. For the original source it changes
  nothing, because `HANDLE` always does `<INT-LEVEL 0>` first and ERROR handlers
  only run below level 8.
- **Other non-local exits:** a RETURN or AGAIN to an activation outside the
  handler, or a GO, still restores the previous level through the delivery
  cleanup. The manual leaves this unspecified. `DISMISS` is not implemented.
- **Primitive failures:** host errors inside SUBRs, unassigned variables and
  wrong arity do not raise the "ERROR" interrupt. This is a strict host failure
  by design (see hypothesis (a)).
- **Not implemented:** error-level LISTEN, `FRAME`/`FFRAME` traversal, ERRET
  without a FRAME, and `FINISH`.
- **Older eligible occurrences:** an occurrence left pending after a raising
  handler is not delivered before the ERROR handler runs. It is delivered after
  the ERROR handler returns normally, or right after ERRET if its priority is
  above the resumed level. Otherwise it waits until the level is lowered.

## Proposed docs/SEMANTICS.md section

Append to "## M3 ERROR interrupt and resumable ERROR frame (source `77rooms.mud:261`)":

> ERROR occurrences are delivered synchronously by the ERROR call itself and
> never enter the session pending queue. An older pending occurrence therefore
> cannot capture an ERROR occurrence, and no occurrence can outlive its FRAME.
> Older eligible occurrences are drained after the ERROR handler returns
> normally, or at a later safe point. The return from ERROR via ERRET is also
> a safe point: once the ERRET level is in force, pending occurrences with a
> priority above it are delivered exactly once, and lower ones stay queued.
>
> Following manual 21.8.11, which tells a resolving handler to do
> `<INT-LEVEL 0>` before ERRET, ERRET resumes the ERROR call at the interrupt
> level that is current when ERRET runs. It does not restore the level from
> before the interrupt, so occurrences queued while the handler ran stay
> queued until the level is lowered. A normal handler return (fallthrough), or a
> host exception leaving a handler, still restores the previous level. FRAME
> liveness ends when the ERROR call is left, in every case.
>
> The rule applies literally to nested errors. Suppose a handler lowers the
> level and calls ERROR again, and the inner handler ERRETs at level 8. The
> inner ERROR returns, and the outer handler continues at level 8 until it
> changes the level itself.
>
> "ERRET keeps the current level" is a documented **inference**, not an
> explicit manual statement. It comes from §21.8.11 (a resolving handler does
> `<INT-LEVEL 0>` and then ERRETs) and §21.7.3 (only `DISMISS` is described
> as choosing or restoring the level on a non-local return). Pinned Confusion
> cannot confirm it: EVENT and HANDLER are stubs there. Other non-local exits
> from a handler, RETURN, AGAIN or GO to an activation outside it, still
> restore the previous level through delivery cleanup. The manual leaves those
> unspecified, and this asymmetry with ERRET is a documented deviation risk,
> not a verified historical rule. `DISMISS` is unsupported.
>
> Primitive (SUBR) failures, unassigned variables and arity errors remain strict
> host failures. They do not raise the "ERROR" interrupt. That would need the
> MDL error-ATOM catalogue and resumable SUBR frames, so it is an explicit,
> documented limitation. It affects the source's ^G and TTY recovery and
> crash-report paths in `HANDLE`.
