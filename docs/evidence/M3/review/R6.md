## The finding

At 850a87f, `mdl-min` (`mdl/runtime/core.rkt:2282`) returned this for zero arguments:

```racket
(mdl-typed-value (mdl-atom "FLOAT") (mdl-word fix-max))
```

That is a FLOAT-tagged WORD sentinel. Every other FLOAT is a host inexact real
(`mdl-type-name`, `core.rkt:2429`). The numeric primitives (`check-number`,
`L?`/`G?`, `0?`/`1?`, `MIN`, `FIX`, `FLOAT`) only accept host reals, so they
rejected the sentinel. Identity and equality compared it by its WORD storage, so
it was never equal to a normal FLOAT with the same value. Only CHTYPE to FIX/WORD
and the bit operations (`ANDB` and others, through `word-bits-of`) accepted it,
and those same operations rejected every ordinary FLOAT.

## How the original source uses the value

There is exactly one use, in `patched_confusion/77dung.mud:57`, which is part of
the 1,229-form load chain:

```mdl
<SETG BIGFIX </ <CHTYPE <MIN> FIX> 2>>
```

`,BIGFIX` is then spliced (`%,BIGFIX`) into many object definitions as an object
size or capacity. The source depends on one thing only: the WORD image of the
greatest FLOAT, cast to FIX and halved. On the 36-bit target that image is octal
377777777777 = 34359738367. So BIGFIX = 17179869183. No other `<MIN>` or `<MAX>`
with zero arguments appears in the source tree. The other `MIN` calls
(`77act1.mud:963`, `77rooms.mud:1590`) pass FIX arguments.

## Manual contract and Confusion observations

Manual, chapter 3 (fetched from mdl-language.readthedocs.io, "03-built-in-functions"):

- §3.5 lists the identities for zero arguments as "`0`, `0`, `1`, `1`, the
  greatest `FLOAT`, and the least `FLOAT`" for `+ - * / MIN MAX`.
- Results that are too large or too small "for the machine's capacity" signal
  overflow or underflow.
- §3.4: one FLOAT argument makes the result FLOAT. `FIX` and `FLOAT` convert
  between the two.
- PDP-10 single-precision format, from memory and unverified against the
  manual: bit 0 is the sign, bits 1–8 are an excess-128 exponent, bits 9–35 are a
  normalized 27-bit fraction, and a negative value is the two's complement of the
  whole word. This gives the known constants 1.0 = 201400000000₈ and
  −1.0 = 576400000000₈. It is consistent with the existing expectation that the
  greatest FLOAT has the image 377777777777₈ = greatest FIX.

reference deviation already noted in `docs/SEMANTICS.md` ("M3 MIN").

## Root cause

`core.rkt:2282-2284` (at 850a87f) gave one value a representation different from
all other FLOATs. It did this so that CHTYPE (`core.rkt:2937-2944`, through
`word-bits-of`) could produce the 36-bit image. CHTYPE had no way to produce the
image of a host FLOAT, so the sentinel stood in for that missing conversion.

## Design decision

There is now one representation:

1. `<MIN>` with zero arguments returns an ordinary host flonum,
   `pdp10-greatest-float` = (2²⁷−1)·2¹⁰⁰ ≈ 1.7014118219281863e38. This is the
   greatest PDP-10 single-precision FLOAT, and a double holds it exactly.
   Arithmetic, comparison, `==?`/`=?`, MIN contagion, `FIX` and `FLOAT` now
   treat it like any other FLOAT.
2. CHTYPE from a FLOAT to a WORD-primtype TYPE (FIX, WORD, or a user WORD
   NEWTYPE) derives the PDP-10 single-precision word image through the new
   `float-word-bits`. That image is 377777777777₈ for `<MIN>`, so BIGFIX keeps
   its 36-bit value. If a host flonum has no exact 36-bit image, CHTYPE raises
   "FLOAT has no exact PDP-10 FLOAT word image" instead of rounding. This covers
   fractions wider than 27 bits (e.g. `0.1`) and exponents outside the
   excess-128 range (e.g. `<* <MIN> 2>`).
3. `word-bits-of` is **not** changed. The bit operations (ANDB, ORB, XORB, EQVB,
   LSH, GETBITS, PUTBITS) still reject FLOAT, as `tests/word_test.rkt` already
   required for `<ANDB 1.0 3>`. `<ANDB <MIN> 1>` now fails the same way. It used
   to succeed only because of the sentinel. Nothing in the source uses it.

The PDP-10 target is chosen over Confusion's host `DBL_MAX` because the runtime
models 36-bit FIX/WORD everywhere. With the host value, CHTYPE would have to give
a 64-bit image, and BIGFIX would no longer fit in a FIX.

## Remaining risks and unsupported cases

- **Host magnitude:** FLOAT arithmetic uses IEEE doubles. Results above the
  PDP-10 range (e.g. `<* <MIN> 2>` ≈ 3.4e38) succeed on the host. The PDP-10
  would signal overflow. CHTYPE of such a value to a WORD type fails strictly.
  A FLOAT range check in arithmetic is a broader FLOAT change and is out of scope.
- **Fraction width:** host FLOATs keep 53-bit fractions, not 27. FLOAT values
  computed from non-dyadic decimals (for example `0.1`) differ from PDP-10
  values in their low bits, and CHTYPE of them to a WORD type fails.
- **Not supported:**
  - CHTYPE from FIX/WORD to FLOAT (decoding an image) still fails with
    "unsupported built-in TYPE conversion";
  - bit operations on FLOAT fail;
  - `MAX` is not implemented (R9 scope);
  - the runtime has no general printer (PRIN1/UNPARSE), so FLOAT printing is
    not covered.
- **Generic host errors:** `L?`, `G?`, `L=?` and `G=?` still call Racket `<`/`>`
  without `check-number`, so a non-number argument gives a host contract error.
  This no longer affects `<MIN>`. It is a separate strictness issue for other
  argument types.
- **FLOAT of a FLOAT:** the runtime accepts it and returns the argument.
  Confusion rejects it with "Arg to FLOAT must be FIX". This is unchanged,
  outside this finding, and recorded here only.
